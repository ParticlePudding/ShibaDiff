## 1. はじめに

### 1.1 目的
本書は文書比較ツール「ShibaDiff」が満たすべき要件を定める。開発・評価・改修の判断基準とする。

### 1.2 対象範囲
- ShibaDiff 本体（単一HTMLファイル）の機能・品質に関する要件
- ビルド・テストの仕組みは、開発を支えるものとして要件の範囲に含める
- 対象外：ファイルの変換ツール（DocuWorks→PDF など）、OCR、サーバー側のしくみ

### 1.3 要件の状態の表記
| 表記 | 意味 |
|---|---|
| 済 | v1.3.0 までに実装済み |
| 2回目 | 次の開発で実装する（採用済み） |
| 3回目 | その次の開発で実装する（採用済み） |
| 保留 | 採否を保留中 |
| 見送り | 実装しない |

## 2. 背景と目的

### 2.1 背景
社内の文書確認業務では、次の2種類のツールを使い分けている。
- **WinMerge**：テキストの差分を確認する
- **DocuWorks Viewer**：文書をページのまま並べて見比べ、付箋などの注釈を付ける

このため、次のような問題がある。
- PDF・Word・Excel の版の違いを確かめるために、テキストへの変換などの手間がかかる
- スキャンした文書や図面の変更箇所は、目視で探すしかない
- ツールのインストールに管理者権限が必要な端末や、外部ネットワークに出られない端末がある

### 2.2 目的
1. テキスト・Office文書・PDF・画像の版の違いを、1つのツールで漏れなく確認できるようにする
2. 確認結果に注釈を付け、印刷・PDF・レポートとして残せるようにする
3. インストール不要・ネットワーク不要で、閉じた社内環境でも安全に使えるようにする

### 2.3 達成の目安
- 20人の業務別レビューで、用意した正解の差分を全員が「漏れなし」と確認できること（v1.0 で達成）
- 全レビュアーが「業務で使いたい」と答えること（v1.0：全員が条件付きで「はい」、平均★3.2／5）

## 3. 利用者と利用場面

### 3.1 利用者
| 区分 | 主な利用者 | 主に使う機能 |
|---|---|---|
| 文書管理・審査系 | 法務、総務（規程管理）、品質保証、自治体の文書管理、薬事 | Word・PDFのテキスト比較、新旧対照、注釈、印刷 |
| 数値・表計算系 | 経理、購買、人事、経営企画 | Excel・CSVの比較、数値の差 |
| 図面・画像系 | 機械設計、施工管理 | 重ね合わせ比較、位置合わせ、スキャン図面 |
| 技術系 | ソフトウェア開発、社内SE、テスト | ソースコード・設定ファイル・ログの比較、パッチ、フォルダ比較 |
| 一般 | 営業、一般事務、テクニカルライター、研究 | 提案書・申請書・マニュアル・論文の版の確認 |

### 3.2 代表的な業務の流れ
```
受け取った修正版を開く
  → 旧版と左右に並べて比較（テキスト／ページ／重ね合わせ）
  → 変更点を1つずつ確認（前へ・次へ）
  → 必要に応じて付箋・枠などの注釈を付ける
  → 印刷・PDF・レポートで記録を残す／上長に回す
```

| FR-X-01 | キー列（社員番号など）で行を突き合わせる比較 | 保留 | 通常の差分とは別のモードとして検討する |
| FR-X-02 | 書式の違う数値（1,000 と 1000）を同じ値とみなす | 保留 | |
| FR-X-03 | 行単位の無視ルール（正規表現） | 保留 | |
| FR-X-04 | 重要語を含む差分の強調 | 保留 | すべての差分を確認する前提のため |
| FR-X-05 | 比較から外す範囲の指定 | 保留 | 操作を複雑にしすぎないため |
| FR-X-06 | 差分を1行ずつ数える | 見送り | まとまった差分は1箇所とするのが正しい |
| FR-X-07 | 提出版に残ったノートの警告 | 見送り | 利用者が自分で確認する |
| FR-X-08 | OCR | 見送り | 本体には入れない。実装する場合は完全に独立したプラグインとする |
| FR-X-09 | 専門用語の言い換え | 見送り | |
| FR-X-10 | 注釈の作成者・日時の記録 | 見送り | 報告をこのツールで完結させることは目指さない |
| FR-X-11 | 元のファイルへの上書き保存 | 見送り | 「名前を付けて保存」で足りる |
| FR-X-12 | .xdw・旧Office形式（.doc/.xls/.ppt）の読み込み | 見送り | 仕様が非公開または作業量が大きい。変換したファイルを用意してもらう |

## 5. 非機能要件

### 5.1 動作環境・配布
| ID | 要件 |
|---|---|
| NFR-ENV-01 | Microsoft Edge・Google Chrome の最新版で動作すること。Firefox・Safari では、保存がダウンロードになるなど一部機能の動きが変わってもよい |
| NFR-ENV-02 | 1つのHTMLファイルとして配布し、インストール・管理者権限・サーバーを必要としないこと |
| NFR-ENV-03 | ローカルのファイルとして開いた状態（`file://`）で、すべての機能が動くこと |
| NFR-ENV-04 | 画面幅 1366×768 のノートPCで実用になること。幅 760px 未満では、それに合わせた配置にすること（タッチ操作専用の処理は持たない） |
| NFR-ENV-05 | ファイルの大きさは数MB程度に抑えること（v1.1.0：約2.5MB） |

### 5.2 性能
| ID | 要件 | 実績（v1.1.0） |
|---|---|---|
| NFR-PF-01 | 1万行程度のテキストを1秒以内に比較できること | 5万行で約1.0秒、10万行で約1.9秒 |
| NFR-PF-02 | 大きなファイルでも、スクロールや差分の移動が遅くならないこと | 仮想スクロールで、表示中の行だけを描画 |
| NFR-PF-03 | 一般的な文書（数十ページ）を数秒以内に開けること | docx・xlsx・pdf：1ファイル 0.3〜0.8秒 |
| NFR-PF-04 | スキャン画像の自動位置合わせは、1ページ数秒以内に終わること | 3〜6秒（回転の推定を含む）。A0 を 200dpi でスキャンしたPDF（9362×6622画素）は、読み込みから結果の表示まで約8.5秒（大半はPDF内の画像の展開） |
| NFR-PF-05 | 処理中も画面が固まらないこと。時間のかかる処理では進み具合を表示すること。PDF の読み込み・描画はワーカー（別スレッド）で行うこと | 863ページの一括チェックでも応答の遅れは0.04秒以下。A0 スキャンの重ね合わせで画面が止まる時間は最長 0.1秒（標準）／0.25秒（精細）（v1.1.2 より前は、ページ表示で最長9.4秒、位置合わせで2.6秒） |

### 5.3 セキュリティ・プライバシー
| ID | 要件 |
|---|---|
| NFR-SEC-01 | 外部と一切通信しないこと。Content-Security-Policy で通信・外部読み込み・eval を禁止すること |
| NFR-SEC-02 | 読み込んだ文書の中身やファイル名に含まれるスクリプト（XSS）が実行されないこと。画面・レポート・パッチのすべてで無害化すること |
| NFR-SEC-03 | 注釈ファイル（JSON）やブラウザに保存されたデータは信用せず、読み込み・保存・描画のたびに検証すること |
| NFR-SEC-04 | PDF内のJavaScriptやリンクは実行しないこと |
| NFR-SEC-05 | ファイルの中身はブラウザに保存しないこと。保存するのは注釈・回転・設定だけとし、利用者が確認・削除できること |
| NFR-SEC-06 | 同梱ライブラリの版を表示し、脆弱性の追跡ができること |

### 5.4 使いやすさ・アクセシビリティ
| ID | 要件 |
|---|---|
| NFR-UX-01 | 色だけに頼らず、記号や線でも差分の種類が分かること |
| NFR-UX-02 | キーボードだけで主な操作ができること（ファイル選択、タブの切り替え、差分の移動、ダイアログ） |
| NFR-UX-03 | ダイアログを開いている間は、キーボードの操作対象をダイアログの中に留め、閉じたら元に戻すこと |
| NFR-UX-04 | 記号だけのボタンには読み上げ用の名前を付けること。文字と背景のコントラスト比は 4.5:1 以上を目安とすること |
| NFR-UX-05 | 文字の大きさを変えられること |
| NFR-UX-06 | 誤解を招く表示をしないこと（例：文字情報のない画像を「同一」と表示しない） |

### 5.5 信頼性
| ID | 要件 |
|---|---|
| NFR-RL-01 | 用意した正解の差分を漏れなく検出すること（全形式） |
| NFR-RL-02 | 壊れたファイルや想定外の形式でも、ツールが停止しないこと。展開後に極端に大きくなる細工したZIP（ZIP爆弾）でも、メモリを使い切らずに読み込みを中止すること |
| NFR-RL-04 | 一部しか表示・比較できないもの（4MB を超えるバイナリなど）について、中身が違うのに「同一」と表示しないこと |
| NFR-RL-03 | 保存していない編集があるときは、閉じる前・別のファイルを読み込む前に確認すること |

### 5.6 保守性
| ID | 要件 |
|---|---|
| NFR-MT-01 | ソースは機能ごとのファイルに分け、ビルドで1つのHTMLにまとめること |

| NFR-MT-03 | headless Chrome で実際に操作する自動テストを用意し、変更のたびに回帰を確認すること。各テストは期待値と照合して合否を判定し、失敗したら終了コードで分かること |

## 6. 制約事項・前提
- DocuWorks 文書（.xdw）は仕様が公開されていないため読み込めない。DocuWorks で PDF に変換して使う
- スキャン画像の文字は読み取らない（OCR なし）。スキャン文書は重ね合わせ比較で確認する
- Word・PowerPoint のページ表示は文字だけの簡易表示であり、元の見た目とは異なる（PowerPoint は3回目で画像表示に対応予定）
- ブラウザの制約で、選んだフォルダへの書き込みや、元のファイルへの上書きはしない
- 注釈はブラウザごとに保存される。別のPCへ移すときは注釈ファイルを書き出して使う

## 7. 用語集
| 用語 | 意味 |
|---|---|
| 差分（のまとまり） | 連続して変わっている行のかたまり。「差分 n 箇所」はこのかたまりの数 |
| 変更／左のみ／右のみ | 左右両方にあって内容が違う行／左にだけある行（削除）／右にだけある行（追加） |
| 行内差分 | 変更行の中で、実際に変わった文字や単語 |
| 一列表示 | 左右に並べず、変更前と変更後の行を1列に並べる表示（git diff に近い） |
| 重ね合わせ比較 | ページを画像として重ね、画素の違いから変更箇所を見つける比較 |
| ずれの許容 | 重ね合わせ比較で、何ピクセルまでのずれを差分としないか |
| パッチ | 差分を `git apply` などで適用できる形式（unified diff）にしたテキスト |
| 康熙部首 | 「⽉」「⽇」など、通常の漢字と見た目は同じだが別の文字コードの文字。PDF から文字を取り出すと混ざることがある |
| CSP | Content-Security-Policy。ブラウザに、通信や外部の読み込みを禁止させる仕組み |
